# Kellmarks 02.00.00

Release date: 2026-08-13

Branch: `dev`

Planned tag on promotion: `v02.00.00`

## Release summary

02.00.00 replaces the original trusted-LAN assumptions with fail-closed network behavior, protected APIs, private storage, strict input validation, atomic concurrency-safe persistence, bounded resource use, structured observability, pinned dependencies, and automated release gates.

## Classification

This is a **breaking security release** with additive controls and bug fixes.

Breaking changes:

- the built-in server is restricted to loopback instead of all interfaces;
- remote and proxied API access requires bearer authentication;
- wildcard CORS is removed;
- Trusted Host enforcement is enabled;
- runtime data moves outside the public assets directory;
- the Flask catch-all static route is removed;
- imported values that violate 02.00.00 validation are rejected;
- Python 3.10 is now the minimum supported runtime.

Preserved interfaces:

- existing API endpoint paths;
- the bookmark entry fields;
- JSON import/export as an object containing `entries`;
- hierarchical tags and Boolean search semantics;
- static read-only demonstration mode.

## Security issues resolved

| Reference | Severity | Resolution |
| --- | --- | --- |
| SEC-001 | High | Loopback-only built-in server, fail-closed remote access, 32-character bearer token, constant-time comparison, exact public/CORS origins, Trusted Host checks, public-Host and proxy boundaries, and auth throttling. |
| SEC-002 | High | Private instance storage, explicit static allowlist, removal of public runtime data and catch-all routing. |
| SEC-003 | Medium/High | Shared HTTP(S)-only URL normalization across API, import, migration, browser fallback, icons, and external results. |
| SEC-004 | Medium/High | Cross-process lock, unique temporary files, `fsync`, atomic replacement, corruption refusal, import and migration backups. |
| SEC-005 | Medium | Request, data, entry, import, tag, URL, query, and path limits. |
| SEC-006 | Medium | Write/auth/external rate controls, bounded upstream response, trusted redirect host, filtered results. |

## Migration procedure

1. Stop the existing server.
2. Copy the complete existing deployment directory or at minimum `docs/assets/data.json` to offline backup storage.
3. Switch to the `dev` branch at the 02.00.00 release commit.
4. Install the pinned runtime dependencies in a fresh virtual environment.
5. Set required environment values. For a reverse proxy, set `KELLMARKS_AUTH_TOKEN`, `KELLMARKS_REQUIRE_AUTH=1`, `KELLMARKS_PUBLIC_ORIGIN`, exact trusted hosts, and HTTPS controls.
6. Start Kellmarks once with the service account.
7. Confirm that the private data file and `data.pre-v02.00.00.json` exist in the instance directory when legacy data was present.
8. Call `/api/health` and verify version `02.00.00` and data schema `2`.
9. Compare entry counts and sample records against the offline backup.
10. Exercise create, update, export, and delete with a disposable entry.
11. Confirm that `/assets/data.json` and `/server/app.py` return `404`.
12. Enable traffic only after the checks pass.

Migration is non-destructive: the legacy source remains untouched and a private pre-migration copy is created. Unsafe legacy records stop startup for manual correction.

## Rollback plan

1. Stop 02.00.00 and preserve its private `data.json`, `.bak`, and pre-migration backup.
2. Restore the prior application artifact or reset the deployment to the recorded pre-release commit `8c80f90e016a3052824ff528de87bc9a2bdb63a1`.
3. Copy `data.pre-v02.00.00.json` or a verified export back to the location expected by the prior version.
4. Restore the prior dependency environment.
5. Bind the prior server to loopback or place it behind compensating authentication, exact CORS, HTTPS, and network firewall controls. The prior version is not safe for direct network exposure.
6. Run health, entry-count, and CRUD checks before restoring traffic.

Forward-created schema-2 entries retain the same core entry fields, but rollback tooling should use a verified export rather than directly replacing files during an active process.

## Validation plan and release gates

The release is gated by:

- unit, integration, security, regression, migration, concurrency, and observability tests;
- Python 3.10 and 3.13 test jobs;
- branch coverage threshold;
- Python compilation and JavaScript syntax validation;
- Ruff and mypy;
- Bandit, secret-pattern scanning, pip-audit, and CodeQL;
- dependency consistency with `pip check`;
- clean virtual-environment installation;
- release/configuration validation;
- 25,000-entry search performance budget;
- live server smoke test.

The release commit must not be promoted or tagged until required CI jobs pass.

## Configuration review

No secret has a built-in default. Wildcard trusted hosts and origins are rejected. Non-loopback use of the built-in server requires both explicit remote mode and a token. HSTS remains opt-in to avoid damaging local HTTP workflows. Default limits are documented in `docs/server/README.md`.

## Database migration review

There is no database schema migration. The JSON document schema increases from version 1 to version 2 while preserving entry fields. The storage location and validation rules change. Migration and rollback are covered by automated tests.

## Performance review

Search remains linear in the entry count. The automated budget executes Boolean search over 25,000 entries and fails above six seconds on the CI runner. File-backed writes remain complete-document operations; high-write or multi-host deployments should move to a transactional database.

## Observability review

Structured request logs and security-denial events were added. Request IDs are returned to clients. No metrics backend is bundled, so deployments should derive request, latency, status, denial, and store-error metrics from JSON logs or add an application telemetry integration.
