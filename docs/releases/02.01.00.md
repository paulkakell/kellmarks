## Delivered scope

Reviewed merge/replacement import for JSON and browser bookmark HTML; conservative URL matching and combined tags; import-wide title/description choices; read-only previews and invalid-entry reporting; concurrency revisions; final count/size validation; private backups and atomic apply. Title, recently-added and recently-updated sort modes. Explicit web-search action, session-only remote-icon consent and the operator external-request switch. A complete roadmap for all eleven accepted feature areas, with planned work clearly separated from implementation.

These changes reduce accidental collection replacement and unrequested external disclosure. Browser import now requires the Flask API rather than silently replacing disconnected local data. Existing browser-local data can still be exported. Per-item duplicate conflict editing, bulk operations, Trash/undo, backup browsing, capture, saved collections, reading status, notes, health checking, preservation, mobile offline sync and AI remain planned. See [ROADMAP.md](../ROADMAP.md) and [USER_GUIDE.md](../USER_GUIDE.md).

## Compatibility and configuration

`POST /api/import` without `mode` keeps its previous replacement contract. New clients use `/api/import/preview`, then an explicit `mode` and returned `baseRevision`; stale state yields `409`. Existing CRUD, Boolean queries, tags, exports, authentication and schema-2 JSON files remain compatible. No database migration or runtime dependency upgrade is required. Existing data is not rewritten at startup solely to change its application version.

`KELLMARKS_EXTERNAL_REQUESTS` defaults to `1` to preserve trusted direct API access. `0` denies the external-search route before networking and blocks remote icons through CSP. Dashboard typing never invokes web search. Icon consent is memory-only and resets on reload. Restart the service and reload open pages after changing operator policy. Normal user-directed navigation remains possible.

The API still has one trusted owner and a bearer-token security boundary, not per-user authorization. Imports do not fetch arbitrary URLs. Future fetching and AI features need the security gates already documented in the roadmap.

## Validation and security review

The implementation adds unit/integration/regression coverage for HTML parsing, validation and limits, conservative duplicate identity, identity collisions, field choices, pure planning, stale revisions, failed backup/write recovery, empty replacement, operator policy and authentication/rate limits. The existing suite remains intact. The quality job additionally runs a real Chromium dashboard script with isolated stores and mocked external services, including mobile layout and cancellation paths.

Local Python 3.13 validation runs compilation, JavaScript syntax, Ruff, mypy over both server modules, Bandit, secret scanning, dependency consistency, the complete pytest suite and the existing plus reviewed-import performance budgets. A local managed browser blocks loopback navigation, so local browser execution is not claimed as passed; GitHub's clean-runner browser result is authoritative for that gate. Exact implementation-commit results belong in PR #10 and the validation ledger before promotion; preparatory-commit checks alone do not establish implementation readiness.

The CI matrix installs pinned dependencies freshly on Python 3.10 and 3.13. The quality job audits runtime dependencies and the separate pinned browser-test tools, runs the server smoke test and benchmarks, and checks release/configuration alignment. CodeQL checks Python and JavaScript. The read-only validation bundle contains tracked source, validation wheels, provenance and SHA-256 checksums, tied to version and exact checkout revision with three-day retention. A PR bundle may identify GitHub's synthetic merge revision; do not mislabel it as the feature-branch head. Runtime data, tokens and untracked files are not included.

Authentication/authorization and secrets handling are unchanged. New API routes inherit the existing security gate and structured request IDs. Preview/apply content is not logged. Backups use existing private permissions and filesystem locking. No multi-file pseudo-transaction, persistent client token, arbitrary server fetch, automatic AI call or widened origin policy was introduced. A dependency audit is not a guarantee against undiscovered vulnerabilities.

## Rollback and restore

Previous code: `b65cd0d71d201a90bc0df7ac1845a0745022cfcf`, incorporating application 02.00.03 at `de40dfa9ebecb6aa48d92c94d9e3b6e13cf40e01` and the newer community configuration. Do not delete prior tags or rewrite historical release files. The application source remains accessible by those immutable commits.

1. Stop the service and other writers. Copy the configured private data file and its `.bak` to a separate protected directory. Verify the copies before any restore; never overwrite the only recoverable backup.
2. Revert the release merge in a new commit, or deploy the previous source artifact. Restore the prior environment configuration. The old version ignores the new switch, so do not rely on that variable to enforce privacy after downgrade; retain network controls and avoid external lookup UI paths.
3. Because schema 2 is unchanged, current data may be retained when downgrading. To undo a particular full import, restore the independently preserved pre-import `.bak` while stopped, or import its copy as explicit replacement after starting the reviewed version. Restoring a whole snapshot also discards later edits, so export those first.
4. Start on loopback, check `/api/health`, verify expected version/schema, count and inspect representative bookmarks, and test authentication before reopening network access. Keep rollback copies until the restored service is verified.

Automated tests rehearse a schema-2 pre-import backup restore through the legacy import contract and verify that failed backup/write operations leave live data unchanged. No schema rollback script is needed. Trash, per-entry rollback and multi-snapshot recovery are not implemented.
